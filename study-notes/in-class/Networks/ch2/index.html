Chapter 2: Application Layer

计算机网络最顶部的层次：应用层

Network Apps

应用层复杂性主要放在 Network Edge，我们称之为“端到端原则”。总之我们希望网络核心只参与简单的转发工作，而将内容处理等任务交给实际的终端。这使得互联网的可扩展性强

一个 Network App 有两种架构：Client-Server 与 P2P

Client-Server 通常会依赖中心服务器，通过客户端联系服务器，由服务商提供服务资源，比较较容易集中管理，但是扩展性受服务商限制

P2P 则是一个去中心化架构，通信双方对等，互相可提供资源、参与节点，难以集中管理，但是新增节点可扩展性强（BitTorrent 是一个典型）

用过种子的都知道，在 P2P 模式中，已经获得文件部分内容的用户也能向其他人上传。新用户虽然增加下载需求，却也可能增加整个系统的上传能力。当然 P2P 并不意味着完全没有服务器，比如 BitTorrent 就会使用 Tracker 来帮助对等方发现彼此

Process communication

网络通信在应用层看来，本质上是不同主机上的进程交换 message。而 socket 是进程与网络（应用层和运输层）之间的接口

Socket（套接字）是应用程序通过操作系统网络协议栈发送和接收数据的编程接口所操作的通信端点

为了接收 messages，进程需要拥有一个 identifier。每个 host 设备都有一个 IP 地址，而单个 host 可以运行多个进程，因此我们额外用 port 端口来进行区分

因此一个 identifier 可以用 IP address + Port Numbers 来表示，并且有一些常用的 port 约定，比如 HTTP 服务对应端口 80

不同的应用对网络要求不同，我们可以划分为四类要求：

  • 可靠性：数据能否完整到达
  • 时延（实时性）：数据能否及时到达
  • 吞吐量：传输数据的速度
  • 安全性：信息是否会被窃取冒充等

因此简单引入一下运输层的两种常见传输方式：TCP 与 UDP，这两种传输方式的传输特性不同，因此应用层会根据自身需求进行选择（具体的内容会在运输层介绍）

TCP 服务 UDP 服务
可靠传输：在发送进程和接收进程之间提供可靠的数据传输 不可靠数据传输：在发送进程和接收进程之间提供不可靠的数据传输
流量控制：发送方不会压垮接收方 不提供：可靠性、流量控制、拥塞控制、时序、吞吐量保证、安全性或连接建立
拥塞控制：当网络过载时，限制发送方的发送速率
面向连接：客户端和服务器进程之间需要先建立连接
不提供：时序、最低吞吐量保证、安全性

UDP + 应用层自行设计可靠传输策略是以实时通信为主的常见方案，当然 UDP 本身还是不可靠的

TCP 即使有了很多功能，依旧不提供加密，因此我们引入 TLS（Transport Layer Security），其主要作用包括加密、完整性保护与端点认证

最终，我们总述一个应用层协议应该具有哪些内容：

  • 消息类型（Request/Response）
  • 消息语法（syntax，如何组织字段）
  • 消息语义（semantics，如何解释字段）
  • 消息交互规则（何时发送、如何响应等）

接下来介绍最基本的 HTTP 应用层协议

Web && HTTP

Web Page 是一个完整页面，而 Web Objects 包含可以由 URL 标识并通过 HTTP 获取的资源（比如 HTML 文件、图片、js 脚本）。一个网页通常包含一个基础 HTML 文件和多个被引用的对象

URL（Uniform Resource Locator）俗称网址，它包含协议、主机名、端口号和路径四个部分，并且可以忽略某些部分的显式描述，比如下面两个网址可能得到一样的页面

1
2
http://www.example.com:80/index.html
example.com

HTTP 使用 TCP 协议，大致流程是：

  • 客户端初始化 TCP 连接（构建 socket）发给服务端
  • 服务端接受 TCP 连接
  • 在浏览器和 Web 服务器之间交换 messages
  • 关闭 TCP 连接

Stateless

HTTP 是一个无状态协议，更严谨地说：HTTP 协议本身不要求服务器保存以前请求的状态，以决定当前请求应如何处理

当然，HTTP 协议是无状态的，但是具体应用可以通过其他方式维持同一个用户的会话，比如在 HTTP message 中携带 cookie；无状态也不代表每次请求都必须重新建立 TCP 连接，这引出了后续的内容

(Non-)Persistent HTTP

HTTP 连接分为两类：非持续性 HTTP 只允许最多一个 Object 通过单条 TCP 连接传输（单次传输后即关闭 TCP 连接）；而持续性 HTTP 允许多个 Objects 在单个 TCP 连接上传输

这对 HTTP 的时延有很大影响：我们定义 RTT 为一个很小的 packet 从客户端到服务端一个来回的时长，单个 Object 大小为 \(F\)，有效传输速率为 \(R\)

  • 非持续 HTTP 的时延为
\[ T=2RTT+\frac{F}{R} \text{ (for every object)} \]

其中第一个 RTT 用于建立 TCP 连接，第二个 RTT 用于一轮资源请求，之后加上文件传输的时间

  • 使用了持续 HTTP 后，考虑 \(n\) 个 Object 的传输，忽视传输时延，我们有
\[ T = 2RTT + (n-1)RTT\text{ (for all objects)} \]

这是因为只有第一个 Object 需要建立 TCP 连接，之后的可以直接复用，于是各自省了一次 TCP 连接

  • 进一步的，考虑一个 HTML 页面 with \(n\) 个图片资源，使用流水线技术并忽视并发上限，有
\[ T = 2RTT + RTT \]

这是因为图片的引用是在 HTML 的基础上的，因此需要先完整的建立 TCP 连接并获取 HTML 内容（2 RTT），了解有哪些资源被引用，再并发获取其他图片资源

Cookie

HTTP 是无状态性的，服务器如何知道多个请求来自同一个浏览器会话？

Cookie 是一个典型的解决方案，它包含四个字段：

  • HTTP Response 中，服务器给浏览器的 Set-Cookie 字段告诉客户端浏览器接下来使用什么 Cookie
  • HTTP Request 中，客户端携带 Cookie 字段
  • 客户端保存的 Cookie 文件
  • 服务端后端的数据库用于记录 Cookie 对应的用户信息（Cookie 的持久化属性取决于这里）

Cookie 的作用比想象中的多。第三方 Cookie 是由正在访问的网站之外的另一个域名设置的 Cookie，比如广告商在不同的网页投放广告时，可以向客户端发送 Cookie，这样一个用户在访问不同的网站时，第三方广告商可以根据 Cookie 关联用户行为，跨站追踪用户，投放定向广告

Web Cache

缓存的目标是让客户端尽量从更近的位置获取对象，而不是每次都得从 Origin 服务器反复拉去内容

Web Cache 的机制和硬件上的缓存比较像：借助独立的 Proxy Server 缓存内容，浏览器根据配置优先向 Web Cache 发送 HTTP 请求，如果 Cache Hit 就直接返回，否则由 Web Cache 向 Origin Server 请求对象，后者返回对象后，Web Cache 在允许缓存时保存对象副本，然后返回对象给浏览器

由此也可见，在 Cache Miss 较频繁的场景，Web Cache 实际会增大代理处理开销，因此其主要性能优势来自后续的缓存命中

源服务器可以通过 HTTP 响应首部向缓存说明该资源允许怎样缓存，比如

1
Cache-Control: public, max-age=3600

就表示响应可由共享缓存保存，最大有效期为 3600s；Cache-Control: no-store 表示禁止存储响应

显然，缓存的内容与源服务器的内容应当保持一致。可能会出现两种情况：

  • 缓存根据 HTTP 缓存规则到期，不再 fresh
  • 缓存对应的原始数据已经被修改

因此我们需要引入 Conditional GET，来确保自己获得的确实是同一份文件

  • Web Cache 在获取 Object 并缓存时，存储 Last-Modified 字段的日期
  • 在请求资源时，Web Cache 携带 If-Modified-Since 字段发起请求，内容为上一次存储的 Last-Modified
  • 源服务器返回 HTTP/1.1 304 Not Modified 或者 HTTP/1.1 200 OK + 新的对象

总之

Web Cache 可以：

  • 减少客户端响应时间
  • 更接近客户端的进行通信
  • 减少机构接入链路的流量
  • 帮助内容提供商更有效地分发资源

相比升级已有的链路带宽，Web Cache 有时具有更低的成本，而缓存命中率会影响这一点，一般会有一类计算题，此处略

HTTP versions

现在标准的三个版本是 HTTP/1.1、HTTP/2、HTTP/3

HTTP/2 相比较 HTTP/1.1 采取了二进制分帧与多路复用，改善了应用层的队头阻塞问题（否则大的 Object 会阻塞小 Object 的传输）

HTTP/3 直接使用了基于 UDP 的 QUIC 机制而不使用 TCP

DNS

之前提到过，一个 identifier 可以用 IP address + Port Numbers 来表示，但是这个纯数字的标识符明显不方便记忆。我们希望用人类可读的主机名来进行映射。于是有了 DNS（Domain Name System，域名系统）

DNS 简单来说就是一个能将 Hostname 映射到 IP Address 的记录系统（还能维护各种别名，以及让单个 Hostname 分担到多个 IP），它是应用层层面的，包含分布式的命名数据库以及对应的查询协议

一方面，DNS 服务器是分布式的，这是为了：

  • 以防单点故障导致全球性的域名解析影响
  • 分流查询压力
  • 缩短不同地区的查询时延
  • 便于分级维护

此外，真正的查询还涉及 Local DNS Server（本地服务器），它负责在设备上向上级 DNS Server 发起查询，或者从缓存中直接获取结果。它通常不属于 DNS 层次树

连 Wi-Fi 时设置的 DNS 地址就是 Local DNS Server，它可以是由路由器通过 DHCP 自动下发的，也可以是手动设置为 8.8.8.8 这种公共 Local DNS Server

DNS Lookup

DNS 查询有两种方法：迭代查询与递归查询，这两种查询的最本质区别在于：谁负责在获取中间结果后继续查询

迭代查询的方式是：始终由发起查询的服务器进行查询，每次从查询结果中获取 IP 地址，或者下一步应该去联系的 DNS 服务器

递归查询的方式是：发起查询的服务器只需要向下一台服务器进行单次查询，被查询的服务器要么给出查询结果，要么递归向下一台服务器发起请求，由后续服务器继续承担工作

实际的工作模型是：客户端向本地 DNS 服务器发起一次递归查询，而本地 DNS 服务器优先查缓存，否则向各级 DNS 服务器发起若干次迭代查询，查询负担集中在本地 DNS 服务器

DNS Cache

Web 都需要缓存，显然 DNS 也需要缓存。通常由 Local DNS Server 进行缓存，它可以降低查询时延，并减轻上层 DNS 服务器的负担

1
2
Host → Local DNS → Root → TLD → Authoritative
Host → Local DNS → Cached IP

DNS 记录中有一条缓存生存时间 TTL，如果在缓存时间内上游存在 DNS 更新，本地 DNS 缓存可能仍会旧的 DNS 信息

此外，本机设备也可能会进行 DNS 缓存

DNS Safety

主要有两种常见攻击：DDoS 和 DNS Spoofing

前者全称为 Distributed Denial of Service（分布式拒绝服务攻击），通过大量流量冲击根服务器等影响全球的查询

后者通过攻击 DNS 服务器伪造 DNS 解析的结果，让正常的域名实际跳转到钓鱼网站。还有一种更接近 Network Edge 的攻击方式是给 DNS 缓存投毒

于是有了 DNSSEC ，它提供数据来源认证和完整性保护，不过不负责加密 DNS 查询内容

P2P

P2P 的结构不同于之前的 Client-Server 结构，所有端都是对等的（Peer），其特点是不需要有始终运行的服务器（但是可以有辅助服务器，比如 BitTorrent 的 Tracker），可以直接建立双端的网络连接（不需要 Server 中转），且双方可以同时是服务的请求方与提供方。这些在之前也提到过了

我们通过一个情境区分 Client-Server 结构与 P2P 结构的不同：

考虑图中的模型，假设网络内部的带宽是巨大的，只需要考虑服务器和 Peer 的吞吐能力：

符号 含义 单位
\(F\) 要分发的文件大小 bit
\(N\) 需要获得文件的 Peer 数量 个
\(u_s\) 服务器上传速率 bit/s
\(u_i\) Peer i 的上传速率 bit/s
\(d_i\) Peer i 的下载速率 bit/s
\(d_{\min}\) 所有 Peer 中最小的下载速率 bit/s

我们记 \(D_{CS}\) 是 Client-Server 结构下，将大小为 \(F\) 的文件分发给全部 \(N\) 个 Peer 所需的整体分发时间的下界，它受到两方面约束

  • 服务器向所有的 \(N\) 个客户端分发完整文件最慢（依次上传）需要
\[ T_{\text{server}}=\frac{NF}{u_s} \]
  • 最慢的客户端下载完整文件用时为
\[ T_{\text{client}}=\frac{F}{d_{\min}} \]

这两件事可以独立进行，因此根据上述的并行约束，可以得到

\[ \boxed{ D_{CS}\geq \max\left\{ \frac{NF}{u_s}, \frac{F}{d_{\min}} \right\} } \]

现在我们来到 P2P 情境，其特点是已经获得文件块的 Peer 也可以向其他 Peer 上传，然而 P2P 依旧存在一定的约束

  • 提供初始资源的 Peer 至少也得向 Network 中上传一份完整的文件
\[ T_1=\frac{F}{u_s} \]
  • 最慢的客户端下载完整文件用时为
\[ T_2=\frac{F}{d_{\min}} \]
  • 所有接收文件的 Peer 最终都需要一份完整的文件，总共需要接收 \(NF\) 大小的数据，而总上传能力上界为 \(u_s+\sum_{i=1}^{N}u_i\)，因此传输 \(NF\) 大小的数据至少用时
\[ T_3=\frac{NF}{u_s+\sum_{i=1}^{N}u_i} \]

因此整体分发下界为

\[ \boxed{ D_{P2P}\geq \max\left\{ \frac{F}{u_s}, \frac{F}{d_{\min}}, \frac{NF}{u_s+\sum_{i=1}^{N}u_i} \right\} } \]

BitTorrent

BitTorrent 是一种用于 P2P 文件共享的通信协议，允许用户利用分散的网络资源分发文件

BitTorrent 为了让新增 Peer 的上传能力更早参与，将单个文件切割成很多 Chunks，让不同的 Peer 以这些 Chunks 作为交换单位，最后所有的 Peers 拼凑出完整文件

我们记正在交换同一个文件的 Chunk 的一组 Peer 称为一个 Torrent，而 Tracker 记录参与某个 Torrent 的 Peer，帮助新加入的 Peer 找到其他节点

当一个用于想要下载文件时，它会加入对应的 Torrent，向 Tracker 服务器获取参与该 Torrent 的 Peer 列表。之后它动态选择一部分节点作为 Neighbors，从这些 Neighbors 出下载自己缺少的 Chunks，并向其他 Peer 上传自己的 Chunks

Strategies

BitTorrent 采用一系列策略来实现高效下载

  • Rarest First：优先请求持有者数量最少的 Chunk 下载

这有助于避免稀缺文件块的丢失，并可提高文件块在网络中的分布程度

  • Tit-for-Tat：通过 choke 策略鼓励用户贡献上传带宽

具体的，BitTorrent 通过每个 Peer 的贡献情况，设定是否给某个 Peer 上传文件块。如果某个 Peer 只下载不上传，那么就会设定这个 Peer 为 Choke 状态，其他 Peers 不会给这个 Peer 上传 Chunks

一种简单的实现就是每个人根据其他 Neighbors 对自己的上传速度排序，选择更快的向它对等上传 Chunks，而对上传速度更慢的不提供 Chunks

当然，对于新加入下载的 Peer 来说，我们引入 Optimistic Unchoking，即：每过一段时间，随机选择一个其他 Peer，允许向其上传数据，这使得刚刚加入 Torrent 的 Peer 也可以快速获得资源

A 随机解封 B，成为 B 的优质上传 Peer；B 也开始向 A 上传数据，也成为 A 的优质上传 Peer

Video Streaming && CDN

视频流是现在互联网带宽的主要消耗者之一

视频流本质是图片的集合，因此我们可以对视频进行编码，比如空间编码（Spatial Coding，利用同一帧图像内部的重复信息减少数据量）与时间编码（Temporal Coding，利用相邻帧之间的相似性，减少需要重复编码的信息）

在编码视频流之后，还需要考虑编码速率，这包括恒定比特率 CBR 和可变比特率 VBR，后者可以通过在内容复杂度高的场景下分配更多比特，在静止场景下分配更少比特

Streaming Stored Video

流媒体可以实现：客户端正在播放视频的前一部分时，服务器仍然在传输视频的后一部分。这使得我们观看视频时可以持续流畅的播放（理想情况）

然而，服务器到客户端的可用带宽随时间变化，并且数据包可能丢失或延迟，其中一个最常见的问题是 Jitter（网络抖动）：不同的数据包以不同的传输延迟抵达，这导致服务端匀速发送 packet，但是客户端不能匀速接收，导致画面出现卡顿

一个显然的方法就是 Playout Buffering，设置一个缓冲区用于积累已下载的视频数据；客户端还可以通过设置 Playout Delay，在收到视频数据后，等待一段时间才开始播放

Playout Buffering 不能消除抖动，这是显然的

DASH

播放缓冲只能解决短期网络波动，如果一个人的网络慢到视频一定无法正常加载资源，就需要别的措施

我们称之为 Dynamic Adaptive Streaming over HTTP，即基于 HTTP 的动态自适应流媒体传输

简单来说就是对于每一个视频 Chunk，选择当前带宽支持的最优画质进行推送。当带宽不足时，通过提供低画质对应的 Chunk 来维持视频的正常播放

即：根据 DASH 原则，客户端应选择当前带宽能够持续支持的最高编码速率

CDN

CDN 即 Content Distribution Network（内容分发网络），就和之前提到的 DNS 分布式查询一样，将内容复制并部署到不同地理位置的服务器上，让用户从合适的服务器获取内容，而不是全部请求远处的源服务器

CDN 的部署方式包含 Enter Deep 和 Bring Home，前者将大量 CDN 服务器深入部署到多个接入网络中，让内容尽可能接近终端用户；后者在靠近接入网络的网络接入点部署数量相对较少、规模较大的服务器集群

由此催生了 OTT（Over-the-Top），指绕过传统有线电视、广播电视等内容分发渠道，直接通过互联网向用户提供内容的服务模式

Socket Programming

为了过渡到下一章的运输层，需要讲解 Socket 编程

Socket 是应用层与运输层之间的接口（不是协议），也分别对应 TCP 和 UDP 两个协议

对于 UDP，发送方不需要进行连接，直接把数据和目标地址发给 Socket，以 Datagram 为单位进行发送，并且不保证顺序到达和完整性（当然，运输层不保证可靠性等，可以在应用层实现这些）

对于 TCP，发送方需要先建立握手连接，然后以字节流为单位提供服务，可以保证顺序到达和完整性，但是不保证一次发送对应一次接收（因为多个数据流可能被一次性接收）

两者的 Socket 类型分别是 SOCK_DGRAM 和 SOCK_STREAM
