Chapter 3: Transport Layer

这一讲是运输层

运输层向应用进程提供端到端的通信抽象，实现应用进程之间的 Logical Communication（逻辑通信）

它的任务只包括将数据交付给目标应用进程，至于如何传输到目标主机是网络层的任务，如何解析数据是应用层的任务

第一章提到，应用层产生的数据，在运输层会为报文添加运输层 Header，存储端口号等内容用于进程间通信，记为 \(H_t\)，形成运输层报文段 \([H_t\mid M]\)。后者是运输层处理和传输的数据单元

运输层协议 TCP 和 UDP 不再介绍，只需要记住：

TCP 相比 UDP 存在连接行为、保证数据可靠传输与按序交付与拥塞控制、流量控制

(De)multiplexing

运输层需要解决这样的问题：发送方如何处理来自多个 Socket 的数据；接收方如何将收到的报文段交给正确的 Socket

发送方的运输层负责从不同 Socket 获取数据，为它们添加相应运输层首部，再将报文段交给网络层，称之为 Multiplexing（多路复用）

接收方的运输层根据 IP 地址、端口号等信息，将报文段交付给正确的 Socket，称之为 Demultiplexing（多路分解）

我们以 demultiplexing 为例，无论是 TCP 还是 UDP，报文段的结构大概是这样的

【16bits 源端口号】【16bits 目的端口号】

【其他 Header】【Payload】

UDP 与 TCP 的多路分解存在一定的区别：

  • UDP 主要根据目的 IP 地址和目的端口号确定接收 Socket，假设有两台客户端向同一个 UDP 服务器发送数据，即使两个报文段的源 IP 或源端口不同，只要它们的目的 IP 和目的端口相同，通常就会被交给同一个 UDP Socket
  • TCP 主要根据 \((\text{源IP},\text{源端口},\text{目的IP},\text{目的端口})\) 的四元组识别 TCP 连接，因此对于上述情况，当 UDP 倾向于交给同一个 Socket 时，TCP 会选择各自的不同 Sockets

UDP

它的特性不需要再介绍了：Connectionless、Best-effort、No extra service

实时通讯、DNS、HTTP/3 都使用 UDP

一个 UDP Segment 只包含 8Byte 的 Header，具体的：

【16bits 源端口号】【16bits 目的端口号】

【16bits 长度】【16bits 校验和】

【Payload】

其中 Length 包含 8Byte 的 Header，而校验和用于初步进行数据传输的错误检测（并不能纠错与重传）

这里我们具体描述一下 Checksum 的计算过程：首先 UDP 校验和的计算范围包含 UDP Header（此时 Checksum 为 0）、Payload，以及由源 IP、目的 IP、协议号等内容临时构造的 Pseudo Header

我们将所有的数据看成一个个 16 位的二进制整数，相加，并将可能的溢出进位作为 +1 加回到结果中（反码求和），得到的结果再按位取反，得到最终的 Checksum

使用校验和时，接收端将所有的数据和 Checksum 一起进行 16 位反码求和，如果结果为全 1 则校验通过

显然，这个校验是脆弱的

Reliable Data Transfer

UDP 脆弱的传输使得数据可能损坏、丢失、乱序化，因此我们需要设计一个协议，从传输层方面获得可靠的数据传输服务

底层信道可能是不可靠的，由 rdt 协议机制实现可靠传输

rdt2.0

现在引入 bit 错误

接收方在通过 Checksum 等检测出错误后，可以向发送方发送两类回复：ACK 和 NAK。前者为 Acknowledgement 的缩写，表示收到正确的 packet，可以发送下一个 packet；后者添加了 Negative 前缀，意味着当前 packet 需要重传

进一步的，为了保障 packet 按照顺序顺利发送，其工作方式为 Stop-and-Wait：在收到当前 packet 的反馈后，发送方才能发送下一个 packet

这个方案有两个问题：

  • Stop-and-Wait 太慢了
  • ACK / NAK 的反馈也可能发生 bit 错误，使得接收方可能将 packet 中的数据重复交付给应用层，或者默认了有问题的 packet 是内容正确的

rdt2.1

rdt2.1 在 rdt2.0 的基础上加入了序列号（Sequence Number）：发送方给 packet 添加序号，接收方利用序号判断这是一个新的 packet，还是之前已经接收过的重复 packet

结合 OI 中滚动数组的思维，不难发现序列号只需要是 0 or 1，用于让接收端区分当前收到的 packet 是上一个的重传，还是正常发来的 packet

Stop-and-Wait 的工作方式决定了发送方每次最多只能有一个已经发送但尚未被确认的 packet

我们称这个序列号的协议为 Alternating-Bit Protocol，这对非 Stop-and-Wait 的工作方式是不可用的

rdt2.2

既然都有了 Alternating-Bit Protocol，我们直接把 NAK 合并到 ACK，只通过 0 or 1 区分当前的 packet 是否顺利发送

此时 ACKx 的作用变成了“最近收到的正确 packet 是这一个还是上一个”

比如发送端发送 pkt1，如果 pkt1 损坏了，则回复 ACK0 而不是 ACK1，表示自己最近收到的正确 packet 还是上一个而不是这个，此时发送端就知道自己需要重传 pkt1；否则回复 ACK1 表示当前 packet 正常收到

rdt2.2 相比 rdt2.1 没有功能上的改进

rdt3.0

现在我们引入新的情况：数据丢失

packet、ACKx 都可能会丢失，或者因为网络问题长时间无法完成传输

于是引入新的机制 Timeout Retransmission（超时重传）：发送方发送数据时启动一个计时器，如果在规定的时间内收到正确的 ACK，就停止计时器，准备发送下一个 packet；否则重新发送当前分组，并重新启动计时器

结合 rdt2.1 引入的序号机制，rdt3.0 可以防止重传导致数据重复交付

需要注意的是：在引入了超时重传机制后，触发重传的唯一条件是超时，而收到非预期的 ACKx 只会进行忽略，不会立刻重传（也不会重置计时器）

假设发送方 waiting for ACK0，但是收到了 ACK1，发送方也只会继续等到超时，或者真的又收到了 ACK0

然而 rdt3.0 的底层工作方式依旧是 Stop-and-Wait，我们考虑发送方真正利用到的时间为

\[ U_{\text{sender}}=\frac{L/R}{RTT+L/R} \]

其中往返时延 RTT 期间，发送方什么都做不了只能等，这段时间被浪费了

Go-Back-N

我们引入流水线机制：拓展序列号的范围为更多的正整数，允许一次可以发送 \(k\) 个 packet并等待确认

\[ U_{\text{sender}}=\frac{kL/R}{RTT+L/R} \]

代价也是有的：需要更大的序号空间，更多的缓存，以及更复杂的错误恢复

因此我们引入完整的 Go-Back-N 机制：考虑一个滑动窗口 \(N\)，其向前移动的唯一条件是窗口最左端的 pkt 收到了对应的 ACK

如果按顺序顺利接收到了 pkt(i)，而接下来的传输超时（这包括收到了非期望顺序的 ACK 值），则接收方只会重复发送 ACKi，并将当前滑动窗口中的所有 packets 全部重传（从 pkt(i+1) 开始）

因此它的名字为 Go-Back-N

经典 Go-Back-N 只需要维护滑动窗口最左端的尚未确认的 packet 的计时器

Selective Repeat

Go-Back-N 的重传机制有些浪费带宽，因此后续提出了 SR 机制：在滑动窗口最左端的尚未确认的 packet 的计时器超时之前，对于乱序抵达的 packets，可以进行独立确认，并且进行接收方缓存。在正确顺序的 ACK 收到后，再从缓存中取出、校验、发给应用层

简单来说，SR 可以乱序接收，保持按序交付

实现上，单个窗口不够用了，发送方需要维护一个发送窗口，其向前移动的唯一条件依旧是窗口最左端的 pkt 收到了对应的 ACK；接收方也需要有一个窗口，接收窗口内收到的 packets（用作缓存，哪怕它是乱序抵达的）

此外，注意到序号和窗口都是有限的，为了确保接收方可以分辨当前的序号对应的是哪一轮的滑动窗口 packets，我们要求

\[ N_{\text{SR}}\leq 2^{k-1} \]

即窗口大小最多为序号空间的一半，其中 \(k\) 是二进制序号的位数

这很好理解：两个完全不重叠的滑动窗口如果占据了超过序号空间大小的长度，根据鸽笼原理，一定有一个序号可能同时出现在两个完全不重叠的窗口中

因此安全的序号空间至少需要容纳两组 \(N\) 个序号

TCP

首先，相比 UDP，以及后面提到的 rdt 等，TCP 将应用层的数据视为连续的字节流，其关键特性是：No message boundaries

TCP 不保证接收方每次收到的内容恰好截止到哪里，信息是没有显式边界的

此外，不同于 UDP 这种无连接的传输，TCP 传输在实现连接后是 Full-duplex 的，在同一条连接中，双方可以同时发送和接收数据

一个 TCP Segment 包含至少 20 Bytes 的 Header，具体的：

【16bits 源端口号】【16bits 目的端口号】

【32bits Sequence Number】

【32bits Acknowledgement Number】

【16bits 长度、标志位】【16bits 接收窗口】

【16bits 校验和】【16bits Urgent Pointer】

...

【Payload】

其中 Sequence Number 表示当前 message 段中第一个数据字节的序号，我们简称为 Seq

Acknowledgement Number 为接收方期望收到的下一个字节的序号，它通常由发送方的上一个 Seq 确定，我们简称为 ACK

Seq：我要从 Seq 开始向你传输数据

ACK：我希望你接下来向我传输的数据从 ACK 开始

具体地说，如果发送方当前要发送的第一个数据字节序号为 1000，发送大小为 300Bytes，那么发送方 TCP 报文段的 Seq = 1000，接收方的 ACK 报文为 ACK = 1300，实际传输的字节范围为 \(1000\sim 1299\)

注意这个和 GBN 等模型的 ACK 不是一个东西，但是 TCP 也可以通过 ACK 的值判断是否发生了丢包。比如如果接收方依旧发送了 ACK = 1000，则说明丢包了需要重传

Timeout

之前我们提到过重传机制，而 TCP 为了决定超时时间，有以下的计算方式

  • SampleRTT

通过实际发送数据和接收 ACK 的时间差测量 RTT，忽略重传的报文段，对多个数据进行平滑估计

  • EstimatedRTT

在此基础上，我们指定一个参数 \(\alpha\)，令

\[ EstimatedRTT=(1-\alpha)EstimatedRTT+\alpha SampleRTT \]

使用指数加权移动平均来动态计算估计值。通常 \(\alpha=0.125\)

  • DevRTT

RTT 的变化范围（方差）也应该纳入考虑，我们用

\[ DevRTT=(1-\beta)DevRTT+\beta|SampleRTT-EstimatedRTT| \]

进一步衡量 RTT 的变化程度。通常 \(\beta=0.25\)

  • 最终获得超时间隔

定义为

\[ \boxed{TimeoutInterval=EstimatedRTT+4DevRTT} \]

Cumulative ACK

根据定义，TCP ACK 是累计的。比如如果两次报文接发，ACK=100 丢失而 ACK=300 收到，则认为 ACK=100 之前的内容也确认收到，接下来可以直接发送 Seq=300

Fast Retransmit

根据 rdt3.0，如果一个 packet 丢失了，只有在超时后才会进行处理

而 TCP 可以通过接收方不断返回的重复 ACK，提前推测数据发生了丢失。我们知道当 ACK 出现重复时，说明最近的传输出现了问题

因此我们设定一个机制：当发送方收到三个重复 ACK 时，不必等待超时，立即重传最早尚未确认的报文段

Flow Control

TCP 的一个功能是实现流量控制，这有助于上面的应用层及时读取数据

因此接收方 TCP 会维护一个缓冲区，等待应用层使用 socket 进行读取。我们记 RcvBuffer 为缓冲区的总大小。rwnd 为剩余可用大小

发送方在收到 rwnd 的大小后，减去自己已发送但是尚未收到 ACK 确认的数据大小，得到自己接下来还能发送的数据量

rwnd 的值在报文结构中，存储在 Receive Window 区域

Connection Management

我们之前提到的内容一直都是传输阶段的，而 TCP 存在“连接”，因此建立连接和断开连接需要有额外的管理

这就是著名的连接时“三次握手”和断开时“四次握手”

首先我们给出 TCP Header 中的标志位

标志位 主要作用
SYN 建立连接，交换初始序号
ACK 表示确认号字段有效
FIN 表示本方向已经没有更多数据要发送
RST 异常中止或拒绝连接

其中 ACK 标志位不等于 ACK Number，前者 ACK 只是个布尔值表示字段是否有效，而后者我们通常写成 Ack

初次连接时，要进行三次握手：

  • 客户端选一个初始序号 x，设置标志位 SYN = 1，携带 Seq = x 发送，进入 SYN_SENT 状态
  • 服务端收到 SYN 后，选一个初始序号 y，设置标志位 SYN = 1, ACK = 1，携带 Seq = y, Ack = x+1 发送，进入 SYN_RCVD

Ack = x+1 是因为客户端的 SYN 也消耗一个序号

  • 客户端收到 SYN+ACK 后，设置标志位 ACK = 1，携带 Seq = x+1, Ack = y+1 发送，直接进入 ESTABLISHED 状态
  • 服务端收到 ACK 后，也进入 ESTABLISHED 状态；否则它会超时重传 SYN+ACK

结束连接时，要进行四次握手

  • 客户端设置标志位 FIN = 1 发送，进入 FIN_WAIT_1 状态
  • 服务端收到 FIN 后，设置标志位 ACK = 1 发送，进入 CLOSE_WAIT 状态，可能会发送剩余的数据
  • 客户端收到 ACK 后进入 FIN_WAIT_2 状态，并等待服务端发送最后的数据，以及 FIN
  • 服务端完成剩余数据传输后，设置标志位 FIN = 1 发送，进入 LAST_ACK 状态
  • 客户端收到 FIN 后，设置标志位 ACK = 1 发送，进入 CLOSED 状态，然后进入 TIME_WAIT 一段时间，最后也 CLOSED

最后一步进入 TIME_WAIT 一段时间是因为客户端最后发送的 ACK 可能会丢失，在这段时间内服务端可以尝试再次发送 FIN 并期待 ACK

通常设置为 2×MSL 的等待时间

注意到结束连接的描述中并没有提到 Seq 和 Ack 的设置，只需要知道：

  • 纯 ACK 不占用额外序号
  • FIN 和 SYN 一样都占用一个序号

巧的是，如果服务器收到客户端 FIN 时，刚好也准备结束自己的发送方向，那么它可以使用一个同时带有 FIN 和 ACK 标志的报文段进行响应。因此实际报文段可以少于四个

Congestion

Flow Control 是为了应用层读取设置的机制，而 TCP 连接同样会影响网络，导致网络拥塞

第一章中便提到，当发送方的总发送量接近链路的满负荷时，只要出现流量波动，就会产生显著的排队情况。进一步的

  • 当因为网速问题进行数据重传时，对网络负载更是雪上加霜
  • 在多跳的传输线路中，如果在靠近下游的位置丢包（比如路由器满载），对上游网络资源的浪费是更显著的

因此需要区分必要重传（完全丢失的 packet）和非必要重传（只是因为 ACK 到达过慢导致的重传），同时引入 Goodput（有效吞吐量）：单位时间内成功交付的、没有重复计算的有效应用数据量

基本的拥塞控制思路包括端到端控制和网络辅助控制

  • 前者：发送方通过网络表现推测拥塞程度，比如丢包率
  • 后者：路由器等网络设备提供明确的拥塞反馈

TCP 在 rwnd 的基础上，引入 cwnd 记录网络拥塞情况，此时发送方允许的最大在途数据量从不超过 rwnd 变成了不超过 \(\min(rwnd,cwnd)\)

我们近似认为 TCP 的发送速率大概为

\[ \boxed{\text{TCP发送速率}\approx\frac{cwnd}{RTT}} \]

那么如何维护 cwnd 的大小？我们引入 AIMD 策略：

  • 网络没有明显拥塞时，每经过约一个 RTT，cwnd 增加 1 MSS，其中 MSS（Maximum Segment Size）为最大的 Payload 长度
  • 网络拥塞时，每次将窗口减半：cwnd /= 2

刚建立 TCP 连接时，发送方不知道网络能够承受多少数据，因此 cwnd 的初始值设置为 1 MSS，并且在一段时间内允许 cwnd 的大小为翻倍增长而不是线性增长。我们称之为慢启动

（具体的实现是，每收到一个 ACK 就让 cwnd 加一，对应为每收到一个 RTT 则翻倍 cwnd）

这个“一段时间”被称为 ssthresh，慢启动阈值

在过了这个阈值后，我们进入拥塞避免环节。之前我们提到过每经过约一个 RTT，cwnd 增加 1 MSS。但是实际上我们需要线性的增长函数。因此实际上，每收到一个 ACK，我们让 cwnd 进行下面的计算

\[ cwnd\leftarrow cwnd+\frac{1}{cwnd} \]

因为一个 RTT 内能收到 cwnd 个 ACK，所以每过一个 RTT，cwnd+1

如果发生了丢包：

  • Timeout 型丢包

则将 ssthresh 减半，并重置 cwnd 为 1，重新进入慢启动

  • 三个重复 ACK

如果是 Reno 模型，则将 ssthresh 减半，并将 cwnd 临时设置为 ssthresh + 3，且每额外收到一个重复 ACK 则 cwnd + 1。在收到确认丢失数据的新 ACK 后重新设置 cwnd = ssthresh。我们称这个操作为快速恢复

如果是 Tahoe 模型则和 Timeout 型丢包一样，减半窗口并重置 cwnd

以上，我们总结 TCP 拥塞控制的三个主要状态（以 Reno 为例）

TCP Throughout

考虑 TCP 的平均吞吐量和 cwnd、RTT 的关系：

我们假设一个理想模型：没有慢启动，使用经典 AIMD，持续发送数据，并假设窗口增长到 W 时发生拥塞，然后减半。那么在稳定之后，AIMD 拥塞窗口的变化大概是这样的

平均窗口大小为

\[ W_{\text{avg}}=\frac34W \]

而

\[ \text{TCP吞吐量}\approx\frac{cwnd}{RTT} \]

因此平均 TCP 吞吐量约为

\[ \boxed{T_{\text{avg}}\approx\frac{3W}{4RTT}} \]

如果不知道 W，我们也希望从丢包率去近似估计平均 TCP 吞吐量：

根据 AIMD 的周期，每增加一个窗口单位大致经过一个 RTT，平均一个拥塞周期内传输了约 \(3W^2/8\) 个报文段，然后发生一次丢包

因为每个 RTT 增加 1，从 0.5W 涨到 W，总共经历了 0.5W 个 RTT

因此积分一下求面积，这部分面积为 \(3W^2/8\)

丢包率 \(p\) 的定义是丢包数 ÷ 发送总数，考虑每次丢包只丢一个包：

\[ p \approx \frac{1}{3W^2/8} \]

整理可得：

\[ W\approx\sqrt{\frac{8}{3p}} \]

因此我们得到 \(W\) 的大致估计，有

\[ \boxed{T_{\text{avg}}\approx\frac{1.22MSS}{RTT\sqrt p}} \]

QUIC

QUIC 是底层基于 UDP 的传输协议，实现了各种传输机制，默认使用在 HTTP/3

之前的 HTTP 访问中，我们会在 HTTP 应用层和 TCP 运输层之间设置 TLS（安全层）负责加密和身份验证，而 QUIC 将其统一，使得只需要大约一个 RTT 的握手即可进行传输

一条 QUIC 连接中可以复用多个相互独立的数据流（Streams）：QUIC 把不同的应用数据组织在多个 Stream 中，某个 Stream 内发生丢包，不必阻塞其他 Stream 已经正确到达的数据（相比之下，TCP 存在队头阻塞问题）
